Why

Many apps need different parts of the same feed, quickly

How it works today

  • An interface engine routes HL7 to each system through hand-built channels.
  • Each team writes its own consumer, parser, and filters, and they drift apart.
  • Analytics reads a separate copy, hours later.

What teams ask for

  • “Alert me within seconds when a potassium result is critical.”
  • “Let me change that threshold today, without a platform release.”
  • “Show me only the columns I'm allowed to see.”

What this builds

  • One parse, in real time, into a schema every app shares.
  • One governed copy in Unity Catalog for BI, audit, and replay.
  • Subscriptions written in SQL. A rule returns the same rows in the SQL editor as it delivers live.

What a rule can do · try one

Any Databricks SQL filter on one record. Errors come back from Databricks.

This preview runs in the page. It mimics the real verdicts from the E2E run and the README. The real check runs in the API: a shape check, then Databricks' DESCRIBE QUERY against the app's own views.

Compared with Fabric Activator

Activator has, and a rule here doesn't: built-in conditions over time ("becomes", "increases", "stays true for", "no data for", averages over 10 s–24 h windows) and a no-code designer.

Here, and not in Activator: rules written in SQL and tested in the SQL editor, registered by each app's code at runtime, and checked against that app's Unity Catalog grants. Matches go to the app's own stream, while Activator sends email, Teams, Power Automate, or Fabric items. The limit is 1,000 rules per hub; Activator allows 500 per item.

Works today: any built-in, applied to one record

CASE, regexp_like, try_cast, abs, date math, IN lists, JSON functions, and so on. The hub applies the same filter the SQL editor does.

Not in a rule: windows and joins by design

A rule sees one record. Rules like “3 rising potassium results in 1 hour” or “no vitals for 30 minutes” need state. The platform builds those once, as a new gold source, using windowed real-time flows (tumbling and sliding windows are GA in Real-Time Mode). Apps then subscribe to that source with a plain filter.

Enrichment happens in the platform, not in each app

Gold records already carry the patient, visit, and code context. Lookups such as unit, attending, or care team are added once, upstream of the hub, with broadcast joins (supported in Real-Time Mode). Every app's rules and notifications then see the same enriched record. next

Security and isolation

Each app reads only what it's granted and receives only its own results

Who is calling?

The app's own service principal

The Databricks Apps proxy authenticates every call and sets the caller's identity. It overwrites forged headers and rejects anonymous calls with 401.

Forged header tested live
What can it read?

Only its granted columns

Each app has Unity Catalog views (sub_<app>.<source>) with only its columns. Databricks compiles rules against those views, so an ungranted column gets UNRESOLVED_COLUMN.

E2E checks 8–9
What can a rule do?

Filter one record

The hub runs filters with its own permissions. Subqueries, joins, and functions that reach outside the record (network, secrets, JVM, UDFs) are refused before Databricks compiles the rule.

E2E checks 12–15 · unit tests
Who reads the results?

Only that app

Each app has its own Event Hub, readable only through its own Unity Catalog service credential. Only that app's service principal has ACCESS on the credential. Unity Catalog issues short-lived tokens, so the app holds no Azure secret.

E2E checks 2–6
Can an app bypass the API?

No

App roles in the operational store can't log in. Only the API acts as them, and row-level security keeps each app to its own rows. The store's Data API is off, and old login roles are dropped.

E2E check 7 · registry tests on Postgres
Where are the secrets?

Not in the platform

Event Hubs has SAS keys disabled, and Spark authenticates with a Unity Catalog service credential. The only secret is the service principal's OAuth secret, kept in the developer's CLI profile. The app won't start if a settings file contains one.

How:

  • Rules are compiled when they change, in the background, not on every batch.
  • Each group of 200 rules runs as one SQL expression.
  • Simple rules are stored as data and matched through an equality index.

A rule beyond the 1,000-rule cap is refused with RULE_LIMIT_REACHED. More rules than that means more hubs (design in docs/SCALABILITY.md).
