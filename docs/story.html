Could it be simpler?

Real-Time Mode reads and writes topics, not tables

The constraint (GA docs, Real-Time Mode in SDP)

Sinks: Kafka, Event Hubs, MSK, and ForEach. Delta is not supported as a real-time source or sink, so a real-time flow can't land on a streaming table directly.

So the shape is: hot path in topics, lakehouse beside it

Each real-time layer writes a topic named after its table. One micro-batch pipeline lands every topic in the streaming table of the same name. It's off the hot path, so it never slows a hop.

If Real-Time Mode gains a Delta sink, the mirror pipeline goes away and nothing else changes.

What it runs, in total

3Real-Time Mode pipelines: bronze, silver, gold (one flow each, as recommended)
1Lakehouse pipeline: every topic → its streaming table
1Subscription hub pipeline (micro-batch: it needs foreachBatch)
1Databricks App: the Subscription API, 2 instances
1Lakebase project: the subscription registry

All serverless. Rebuilt from scratch with make up + make demo dev.

The Java developer's view

Write SQL in your code. Run. Receive.

// MySubscriptions.java: the whole contract rules.put("critical-potassium", """ SELECT patient_id, value_num, units FROM gold_observations WHERE observation_cd_desc = 'Potassium' AND value_num >= 6.5""");
  • Test it first in the SQL editor against your own view, hl7_rtm_demo.sub_<app>.gold_observations. The rows it returns are the records you'll get.
  • The code is the source of truth. On start the app declares exactly this set; anything deleted is cancelled.
  • Your own identity: a service principal profile. No Azure secret: Unity Catalog mints the Event Hubs token.

Databricks says no, in the same call, and nothing is applied

A preview that runs in this page, modeled on the real verdicts from the E2E run and README. The real check is the API: a shape check, then Databricks' DESCRIBE QUERY against the app's own views.

The only rule logic of our own: the shape

SELECT <columns> FROM <one gold source> WHERE <filter>, with any Databricks built-in.

No joins, subqueries, CTEs, aggregates, parameters, or functions that reach outside the record (http_request, secret, ai_*, UDFs). The hub evaluates filters with its own permissions, so a rule must stay one filter over one record.

Everything else is Databricks

Misspelled or ungranted column, wrong type, unknown source: Databricks' own error class, passed through unchanged. The API is a facade, not a second SQL dialect.

Governed by design

Each app sees only what it's granted, and only its own results

Guarded by 24 live E2E checks (--e2e) and the registry tests on a real Postgres. Multi-app isolation with three live service principals is the next test.

Above the cap, a new rule is refused with RULE_LIMIT_REACHED. Past 1,000: more hubs (shards), designed in docs/SCALABILITY.md.

1 · Compile per change, not per batch

A background thread recompiles when the registry changes; batches keep the last compiled set. 67 s → 5.5 s.

2 · One SQL expression per 200 rules

Not a dozen Column calls per rule: each call is a driver round trip.

3 · Simple rules are data

col = 'x' AND n >= 6.5 becomes rows, joined through an equality index. The plan is the same size for 1 or 1,000 rules.
